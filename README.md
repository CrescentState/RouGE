# RouGE — Route-Gated Execution

**RouGE** is a recursive, VRAM-gated routing prototype for heterogeneous quantized LLM inference on edge GPUs. It sits in front of two locally hosted llama.cpp engines — an **INT4** and an **INT8** quantization of the same base model (Qwen 2.5 1.5B Instruct) — and routes work between them based on prompt complexity and live GPU memory.

## How it works

For every prompt, RouGE:

1. **Classifies** each clause as summarization, extraction, code generation, creative writing, or unknown and assigns entropy (`simple` / `complex` / `mixed_intent`) using prototype-bank embeddings with length-aware escalation — `classifier/`.
2. **Decomposes** complex / mixed-intent prompts into a bounded dependency DAG of at most four essential sub-tasks per step, generated by the low-cost INT4 engine with JSON-schema-constrained output — `DAG/`.
3. **Gates** recursion on live GPU memory: if free VRAM exceeds the estimated cost plus a safety margin, a node is decomposed further; otherwise it becomes a leaf — `DAG/decompose.py`.
4. **Executes** leaf sub-tasks sequentially on INT8, passes completed dependency results to downstream tasks, then uses token-budgeted hierarchical synthesis to produce one complete answer — `pipeline.py` + `Setup/api.py`.

Failures degrade gracefully: if the INT4 decomposition fails validation (malformed graph, cyclic edges, bad intent tags), the node is routed to the INT8 engine instead ("Phase 2.5 fallback").

> **Implementation status — read this before trusting section 4:**
> - Leaf execution remains sequential and uses the INT8 engine.
> - The real classifier is integrated into the pipeline and its labels are shared with the DAG layer.
> - Multiple leaf results are synthesized by INT8; oversized synthesis inputs are reduced in bounded batches before the final call.

## Repository layout

```
classifier/   Contract 1 — clause segmentation, prototype-bank embedding,
              entropy labeling, aggregation (unit-tested)
DAG/          Contract 2 — DAG schema validation (dag_models.py) and recursive
              VRAM-gated decomposition (decompose.py)
Setup/        Contract 3 — FastAPI engine + telemetry server (api.py),
              Hugging Face model downloader (download_models.py), Windows
              CUDA/NVML preflight (windows_preflight.py)
ui.py         Streamlit end-to-end pipeline dashboard (root, intentionally)
pipeline.py   Classify → decompose → execute → synthesize orchestration
benchmark.py  Direct-INT8 vs middleware execution, run telemetry, CSV history
setup_windows.bat One-time native Windows/RTX 5050 dependency and model setup
start_rouge.bat   Checked Windows launcher: API readiness wait + UI
pyproject.toml    Single source of truth for dependencies (uv.lock locks it)
requirements-windows.txt / requirements-linux.txt
              Platform-specific alternatives for pip-based installation
```

## Component contracts

| Contract | Producer | Consumer |
|----------|----------|----------|
| 1 — `ClassificationResult` JSON (clauses + aggregate label) | `classifier/` | DAG decomposition, UI |
| 2 — `ValidatedDag` JSON (nodes + edges + topological order) | `DAG/dag_models.py` | `DAG/decompose.py`, UI |
| 3 — Engine HTTP API (`POST /generate`, `GET /telemetry`) | `Setup/api.py` | `DAG/decompose.py`, UI |

## Platform setup

### Shared requirements

- NVIDIA GPU with enough VRAM to hold the Q4 and Q8 models simultaneously;
  the target system is an 8 GB RTX 5050.
- Current NVIDIA driver with working `nvidia-smi` and NVML access.
- Python 3.13 and [uv](https://docs.astral.sh/uv/).
- Approximately 3 GB of storage for the two GGUF model files, in addition to
  the Python environment and model caches.
- Network access during initial dependency and model installation.

RouGE loads both models when the API starts. Begin with a 2048-token context and
a batch size of 256 on an 8 GB card. Increase them only after the conservative
configuration starts successfully.

### Windows 10/11 with RTX 5050

Windows uses the CUDA 13.0 `llama-cpp-python` wheel for native Blackwell
support. Install an R580-or-newer NVIDIA Game Ready or Studio driver and the
Microsoft Visual C++ 2015–2022 Redistributable before setup.

#### First-time setup

Open **Command Prompt**, change to the repository, and run:

```bat
cd C:\path\to\RouGE
setup_windows.bat
```

`setup_windows.bat` performs the following operations:

1. Confirms that `uv`, `nvidia-smi`, and an NVIDIA GPU are available.
2. Creates `.venv` and installs the locked project dependencies without the
   Linux CUDA wheel.
3. Installs `llama-cpp-python 0.3.35` from the CUDA 13.0 wheel index.
4. Runs `Setup\windows_preflight.py` to verify Windows x64, NVML, driver
   version, CUDA support, GPU name, and visible VRAM.
5. Downloads the Q4 and Q8 GGUF files into `Setup\models` when they are absent.

The setup script requires an R580-or-newer driver because CUDA 13 applications
are not supported by older Windows driver branches.

#### Start the application

For every subsequent session, run:

```bat
cd C:\path\to\RouGE
start_rouge.bat
```

The launcher:

- Uses paths relative to the batch file, so it also works when launched from a
  shortcut or another directory.
- Defaults to `ROUGE_CONTEXT_SIZE=2048` and `ROUGE_BATCH_SIZE=256`.
- Checks that the environment and both model files exist.
- Reuses an already healthy RouGE API instead of loading duplicate models.
- Starts the API on `127.0.0.1:8000` and polls `/telemetry` for up to 180
  seconds before starting Streamlit.
- Starts the UI on `127.0.0.1:8501`.

To try the larger context after the default configuration works:

```bat
set ROUGE_CONTEXT_SIZE=4096
set ROUGE_BATCH_SIZE=512
start_rouge.bat
```

These variables affect only that Command Prompt session. Return to 2048/256 if
model initialization reports a CUDA allocation or compute-buffer failure.

#### Windows troubleshooting

| Error | Action |
|---|---|
| `nvidia-smi was not found` | Install or repair the NVIDIA driver, then reopen Command Prompt. |
| Driver is older than R580 | Install a current Game Ready or Studio driver. |
| `llama-cpp-python is not CUDA-enabled` | Run `setup_windows.bat` again; do not replace its CUDA wheel with the PyPI CPU build. |
| CUDA or DLL import failure | Install the Visual C++ 2015–2022 Redistributable and rerun setup. |
| `failed to allocate compute pp buffers` | Close other GPU applications and use context 2048 with batch 256. |
| API readiness timeout | Read the separate **RouGE API Server** window; it retains the startup traceback. |
| Model file missing | Run `setup_windows.bat` to download the missing GGUF file. |
| Another API is already running | Use the existing server or close it before starting another instance. |

### Linux with NVIDIA GPU

The locked Linux environment currently uses the CUDA 12.4
`llama-cpp-python` wheel. A compatible NVIDIA driver and CUDA runtime libraries
must be accessible to the process. The current project has been run with the
Ollama CUDA v12 runtime exposed through `LD_LIBRARY_PATH`; use the CUDA library
location installed on your own machine if it differs.

#### First-time setup

From the repository root:

```bash
cd /path/to/RouGE
uv sync

cd Setup
../.venv/bin/python download_models.py
cd ..
```

The downloader always writes the models to `Setup/models`, regardless of the
directory from which it is invoked.

#### Start the API

Open the first terminal:

```bash
cd /path/to/RouGE/Setup

ROUGE_CONTEXT_SIZE=2048 \
ROUGE_BATCH_SIZE=256 \
../.venv/bin/python -m uvicorn api:app --host 127.0.0.1 --port 8000
```

If `llama_cpp` cannot locate its CUDA shared libraries, add the correct runtime
directory. The following is the path used by an Ollama CUDA v12 installation;
it may not exist on other systems:

```bash
LD_LIBRARY_PATH=/usr/local/lib/ollama/cuda_v12 \
ROUGE_CONTEXT_SIZE=2048 \
ROUGE_BATCH_SIZE=256 \
../.venv/bin/python -m uvicorn api:app --host 127.0.0.1 --port 8000
```

Wait until both INT4 and INT8 models finish loading before starting the UI.

#### Start the UI

Open a second terminal:

```bash
cd /path/to/RouGE

HF_HUB_OFFLINE=1 \
TRANSFORMERS_OFFLINE=1 \
.venv/bin/python -m streamlit run ui.py --server.address 127.0.0.1
```

The offline variables prevent the classifier from making network requests after
its embedding model is cached. Omit them on the first run if MiniLM has not been
downloaded; the classifier can otherwise fall back to its deterministic lexical
embedding backend.

To use the larger context after successful startup, restart the API with:

```bash
ROUGE_CONTEXT_SIZE=4096 \
ROUGE_BATCH_SIZE=512 \
../.venv/bin/python -m uvicorn api:app --host 127.0.0.1 --port 8000
```

#### Linux troubleshooting

| Error | Action |
|---|---|
| `libcudart.so` or another CUDA library is missing | Add the installed CUDA runtime directory to `LD_LIBRARY_PATH`. |
| NVML cannot access GPU 0 | Verify `nvidia-smi`, driver installation, permissions, and container GPU passthrough if applicable. |
| `failed to allocate compute pp buffers` | Stop duplicate LLM processes and retry with context 2048 and batch 256. |
| `Another RouGE API process is already...` | Reuse the server already listening on port 8000 or stop it cleanly. |
| Model file missing | Run `.venv/bin/python Setup/download_models.py` from the repository root. |
| UI cannot reach API | Verify `curl http://127.0.0.1:8000/telemetry` before starting Streamlit. |

### Verify either installation

Once the API and UI are running:

- UI: `http://127.0.0.1:8501`
- API documentation: `http://127.0.0.1:8000/docs`
- Telemetry check: `http://127.0.0.1:8000/telemetry`

Enter the same prompt once with **Normal Direct INT8** and once with **RouGE
Middleware** to populate the answer and telemetry comparison.

## Tuning constants

| Constant | Value | Location |
|---|---|---|
| Classifier confidence floor | 0.45 (0.20 hash-fallback) | `classifier/contracts.py` |
| Classifier best–second margin | 0.08 (0.01 hash-fallback) | `classifier/contracts.py` |
| Length escalation threshold | 4000 tokens | `classifier/entropy.py` |
| Max decomposition depth | 4 | `DAG/decompose.py` |
| Max nodes per decomposition | 4 | `DAG/dag_models.py` |
| Decomposition VRAM cost estimate | 350 MB / node | `DAG/decompose.py` |
| VRAM safety margin | 512 MB | `DAG/decompose.py` |
| Telemetry fallback (server down) | 2048 MB free | `DAG/decompose.py` |
| Model context | Library default 4096; Windows launcher default 2048 (`ROUGE_CONTEXT_SIZE`) | `Setup/generation.py`, `start_rouge.bat` |
| Prompt-processing batch | Library default 512; Windows launcher default 256 (`ROUGE_BATCH_SIZE`) | `Setup/generation.py`, `start_rouge.bat` |
| Leaf output reserve | 512 tokens | `pipeline.py` |
| Final output reserve | 1024 tokens | `pipeline.py` |
| Intermediate reduction output | 256 tokens | `pipeline.py` |
| Context safety margin | 128 tokens | `Setup/generation.py` |
| Maximum executable leaves | 4 | `pipeline.py` |

## Evaluation logs

The API server appends two CSVs under `Setup/`, independent of the directory
from which it was launched:

* `telemetry_log.csv` — GPU telemetry once per second (used/free VRAM, power, temp, util)
* `request_metrics.csv` — one row per `/generate` call (request_id, baseline mode, engine, latency)

The Streamlit benchmark runner also writes:

* `evaluation/benchmark_runs.csv` — one aggregate row per Normal or Middleware run
* `evaluation/benchmark_samples.csv` — raw 200 ms GPU samples keyed by run ID

The benchmark UI compares end-to-end time, estimated GPU energy, power, peak
VRAM, temperature, and utilization for the latest opposite-mode run with the
same SHA-256 prompt fingerprint. These are whole-device measurements, so close
unrelated GPU workloads and repeat each mode before drawing conclusions.

## Known limitations

- Leaf execution is sequential; parallel scheduling is not implemented.
- `api.py` endpoints are `async` but call blocking llama.cpp methods — requests serialize and block the event loop.
- If `/telemetry` is unreachable, `decompose()` optimistically assumes 2048 MB free.
- The current server still requires both Q4 and Q8 models plus a working NVIDIA/CUDA environment.

## Baselines & evaluation (planned)

The four comparison conditions (Always-INT8, monolithic, fixed-depth decomposition, full gated recursion) are not yet implemented; they are intended to be config presets over a shared harness.
