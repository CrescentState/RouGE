# RouGE — Route-Gated Execution

**RouGE** is a recursive, VRAM-gated routing prototype for heterogeneous quantized LLM inference on edge GPUs. It sits in front of two locally hosted llama.cpp engines — an **INT4** and an **INT8** quantization of the same base model (Qwen 2.5 1.5B Instruct) — and routes work between them based on prompt complexity and live GPU memory.

## How it works

For every prompt, RouGE:

1. **Classifies** each clause by task type and entropy (`simple` / `complex` / `mixed_intent`), using prototype-bank embeddings with a length-aware escalation model — `classifier/`.
2. **Decomposes** complex / mixed-intent prompts into a dependency DAG of sub-tasks, generated by the low-cost INT4 engine with JSON-schema-constrained output — `DAG/`.
3. **Gates** recursion on live GPU memory: if free VRAM exceeds the estimated cost plus a safety margin, a node is decomposed further; otherwise it becomes a leaf — `DAG/decompose.py`.
4. **Executes** the leaf sub-tasks on the engines via the HTTP API and returns the answers — `Setup/api.py` + `ui.py`.

Failures degrade gracefully: if the INT4 decomposition fails validation (malformed graph, cyclic edges, bad intent tags), the node is routed to the INT8 engine instead ("Phase 2.5 fallback").

> **Implementation status — read this before trusting section 4:**
> - Parallel INT4 execution and output **stitching are not implemented yet**. Today the UI executes every leaf **sequentially on the INT8 engine**.
> - The UI's Phase 1 still uses a **placeholder classifier** heuristic. The real `classifier/` module is complete and unit-tested but is not yet wired into `ui.py`.
> - The INT8 fallback response produced inside `decompose()` is currently **discarded**; the UI re-executes fallback nodes itself.

## Repository layout

```
classifier/   Contract 1 — clause segmentation, prototype-bank embedding,
              entropy labeling, aggregation (unit-tested)
DAG/          Contract 2 — DAG schema validation (dag_models.py) and recursive
              VRAM-gated decomposition (decompose.py)
Setup/        Contract 3 — FastAPI engine + telemetry server (api.py),
              Hugging Face model downloader (download_models.py)
ui.py         Streamlit end-to-end pipeline dashboard (root, intentionally)
start_rouge.bat   One-click launcher: API server window + UI
pyproject.toml    Single source of truth for dependencies (uv.lock locks it)
```

## Component contracts

| Contract | Producer | Consumer |
|----------|----------|----------|
| 1 — `ClassificationResult` JSON (clauses + aggregate label) | `classifier/` | DAG decomposition, UI |
| 2 — `ValidatedDag` JSON (nodes + topological order) | `DAG/dag_models.py` | `DAG/decompose.py`, UI |
| 3 — Engine HTTP API (`POST /generate`, `GET /telemetry`) | `Setup/api.py` | `DAG/decompose.py`, UI |

## Quick start

**Prerequisites:** NVIDIA RTX 5050-class GPU (8 GB VRAM), [NVIDIA CUDA Toolkit 12.4](https://developer.nvidia.com/cuda-12-4-0-download-archive) on `PATH`, Python 3.13, and [uv](https://docs.astral.sh/uv/).

```powershell
# 1. Install dependencies into .venv (pyproject.toml + uv.lock)
uv sync

# 2. Download the GGUF models (runs from Setup/, writes Setup/models/)
cd Setup
..\.venv\Scripts\python.exe download_models.py

# 3. Start the engine + telemetry server (also in Setup/)
..\.venv\Scripts\python.exe -m uvicorn api:app --host 0.0.0.0 --port 8000
```

In a second terminal:

```powershell
# 4. Start the evaluation UI
.venv\Scripts\python.exe -m streamlit run ui.py
```

Open `http://localhost:8501`, enter a prompt, and hit **Execute Pipeline**.
API docs (Swagger): `http://localhost:8000/docs`.

**One-click alternative:** run `.\start_rouge.bat` from the root — it boots the API server in a background window, waits a fixed 10 s for model load, then launches the UI.

## Tuning constants

| Constant | Value | Location |
|---|---|---|
| Classifier confidence floor | 0.45 (0.20 hash-fallback) | `classifier/contracts.py` |
| Classifier best–second margin | 0.08 (0.01 hash-fallback) | `classifier/contracts.py` |
| Length escalation threshold | 4000 tokens | `classifier/entropy.py` |
| Max decomposition depth | 4 | `DAG/decompose.py` |
| Decomposition VRAM cost estimate | 350 MB / node | `DAG/decompose.py` |
| VRAM safety margin | 512 MB | `DAG/decompose.py` |
| Re-decompose token threshold | 30 tokens | `DAG/decompose.py` |
| Telemetry fallback (server down) | 2048 MB free | `DAG/decompose.py` |

## Evaluation logs

The API server appends two CSVs in its working directory (`Setup/` when run as above):

* `telemetry_log.csv` — GPU telemetry once per second (used/free VRAM, power, temp, util)
* `request_metrics.csv` — one row per `/generate` call (request_id, baseline mode, engine, latency)

## Known limitations

- UI Phase 1 is a placeholder heuristic; `classifier.classify()` is not yet wired into `ui.py`.
- No parallel INT4 execution or output stitching (README of the design describes these as intended).
- `api.py` endpoints are `async` but call blocking llama.cpp methods — requests serialize and block the event loop.
- The INT8 fallback text produced inside `decompose()` is discarded (the UI re-executes the node).
- If `/telemetry` is unreachable, `decompose()` optimistically assumes 2048 MB free.
- Threshold mismatch: DAG re-decomposes at 30 tokens while the classifier escalates at 4000.

## Baselines & evaluation (planned)

The four comparison conditions (Always-INT8, monolithic, fixed-depth decomposition, full gated recursion) are not yet implemented; they are intended to be config presets over a shared harness.
